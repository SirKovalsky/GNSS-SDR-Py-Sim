# GNSS Sim — имитатор сигналов L1 (GPS, Galileo, SBAS, QZSS)

Чистый Python (NumPy) генератор комплексной огибающей сигналов L1 и BeiDou
B1I: **GPS L1 C/A**, **GPS L1C**, **Galileo E1**, **SBAS L1 C/A**,
**QZSS L1 C/A** и **BeiDou B1I** (1561.098 МГц). Для B1I реализованы
2046-чиповый код, вторичный код **NH20** (1 кбит/с), сообщение **D1**
(50 бит/с: BCH(15,11,1), 30-битное чередование, реальные эфемериды).
Результат либо пишется в I/Q-файл, либо передаётся потоком на **USRP B210**
через UHD. Интерфейс — PyQt5, есть CLI и карта OpenStreetMap
для построения маршрутов.

Системы выбираются галочками **«Сигналы»** — это единственный источник истины.
Диапазон (`l1`/`b1i`/`all`), центр/`fs` и источник RINEX выводятся
автоматически и **консервативно**: только BeiDou B1I → `b1i`
(1561.098 МГц, 4.092 Мвыб/с); без BeiDou → `l1` (1575.42 МГц, 2.6 Мвыб/с);
B1I вместе с любым L1/E1 по умолчанию оставляет узкую `l1`, а B1I отключается с
понятным сообщением. Единый широкий поток L1+B1I (~1571.33 МГц / ~25 Мвыб/с,
боковые лепестки BOC(6,1) сохраняются) включается только явно — галочкой
**«Объединять L1+B1I»** в GUI или флагом `--combine` (CLI — обязательно вместе
с `--beidou`; `--band all`/`wide` — эквивалент). У B210 **один общий TX LO**, поэтому одновременная работа всех
диапазонов возможна только одной полосой. В CLI остаются явные
`--band l1|b1i|all|wide` и ручное переопределение `-s`/`-f`; в GUI центр/`fs`
показаны только для чтения. `wide` — устаревший синоним `all`.

> **BeiDou B1I временно отключён по умолчанию** (в GUI галочка снята, поля B1I
> неактивны). В CLI он включается **только явным** `--beidou`; сессии/флаги
> `--band b1i|all|wide`, `--combine` и `--b1i-data` действуют лишь вместе с ним
> (иначе используется узкая сессия `l1`, а B1I отбрасывается с сообщением).

Реализация не использует C-код `gps-sdr-sim` / `multi-sdr-gps-sim` во время
работы: орбитальная модель, эфемериды, коды и модуляция портированы на Python
и проверены по ICD (IS-GPS-200 / IS-GPS-800 / IS-QZSS / Galileo OS SIS ICD).

## Что реализовано

| Сигнал | Состояние |
|---|---|
| GPS L1 C/A — BPSK(1), 1.023 Мчип/с, NAV (5 подкадров, чётность, TOW) | Полностью |
| GPS L1C — L1Cp TMBOC(6,1,4/33) + L1Cd BOC(1,1), 0.75/0.25 | Коды, L1Co и модуляция полностью |
| Galileo E1 — CBOC(6,1,1/11), E1-B (данные) + E1-C (пилот, вторичный код 25) | Полностью: реальный I/NAV 250 бит/с (FEC ½ K=7, интерливер 30×8, CRC-24Q, слова 1–6) |
| SBAS L1 C/A — PRN 120…158 | Полностью: DO-229 сообщения 250 бит/с (MT1/2-6/9/17/24/25/26/63, CRC-24Q); MT9 самосогласован с передаваемым положением GEO |
| QZSS L1 C/A — PRN 193…206 | Коды и NAV полностью |
| BeiDou B1I — BPSK(2), 2.046 Мчип/с, 2046-чиповый код | Код + NH20 + D1 (BCH(15,11,1), чередование, эфемериды/toe/toc/af0..af2); TGD, ионо и UTC — нули (TODO) |
| CNAV-2 (данные L1Cd) | Пока заглушка; FEC — в разработке |

Коды сверяются с таблицами ICD: C/A (в т.ч. SBAS/QZSS) — по «первым 10 чипам»;
L1Cp/L1Cd/L1Co — по «первым/последним 24 чипам» (self-tests).

**SBAS GEO — синтетические.** Реальные геостационарные SBAS-спутники не
передаются: движок ставит три GEO (PRN 120/123/126) в точку с долготой
`lon + {-15, 0, +15}°`, широта 0, высота ~42164 км (`engine.SBAS_DEFAULT`), а
их MT9/MT17 самосогласованы с этим положением. Поэтому SBAS виден почти всегда
в средних широтах: например, `50N/10E` → S120/123/126 с элевацией 31–33°,
`60N/30E` → 21–22°. Для приёма SBAS выбирайте эти координаты (а не полюс/океан).

**Galileo: health/BGD (почему приёмник берёт лишь часть видимых).** Поле
I/NAV word 5 несёт **раздельные** `BGD E5a/E1` (`Ephemeris.tgd`) и
`BGD E5b/E1` (RINEX orbit-6, поле 4 → `Ephemeris.bgd_e5b`), а также 2-битные
`E1-B HS`/`E5b HS` и биты `DVS`. Раньше в оба поля BGD писался `tgd` (E5a), а
**любое** ненулевое 9-битное RINEX-«SV health» объявляло `E1-B HS = 1` — так
спутник, у которого помечен только E5a/E5b (например, `svhlth = 16`), для
приёмника становился «нездоровым по E1-B» и **выпадал из решения** (оставался
лишь узкий набор видимых вроде E3/E8/E16 с полностью нулевым health).
Теперь health раскладывается по битам RINEX (`e1b_dvs = bit0`, `e1b_hs =
bits1-2`, `e5b_dvs = bit6`, `e5b_hs = bits7-8`, см.
`galileo_nav.galileo_health`), E1-B HS передаётся корректно, а BGD E5b — из
отдельного поля. Уровень E1 не менялся (E1-B+E1-C, CBOC, нормировка
`1/√2`; мощность суммарно совпадает с L1 C/A, проверено тестами).


## Установка

Проект **самодостаточен**: нужен только Python 3.10–3.13 и (для передачи на
B210) UHD. Для UHD/B210 используйте Python **3.12**: пакет `uhd` собран против
NumPy 1.x, а у NumPy 1.x нет wheel'ов под 3.13. На 3.13 работает генерация IQ в
файл (NumPy 2.x). Виртуальное окружение создаётся **внутри проекта** — `.venv`.

### Windows (PowerShell)

```powershell
cd E:\MySoftware\GNSS_Sim
.\scripts\setup_windows.ps1
```

Скрипт создаёт `.venv` (`py -3.12 -m venv .venv`), обновляет pip, ставит
`requirements.txt`, при наличии UHD-библиотек (`uhd.dll` или `UHD_PKG_PATH`)
ставит `uhd==4.10.0.0`, а на NVIDIA-машине (флаг `-Cuda`) —
`cupy-cuda12x<14` вместе с runtime-пакетами `nvidia-*-cu12` (cudart/NVRTC),
так что отдельный CUDA Toolkit не нужен.

Вручную:

```powershell
cd E:\MySoftware\GNSS_Sim
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# UHD (только для B210): скачать и запустить Windows-инсталлятор UHD
# (https://files.ettus.com/binaries/uhd/latest_release/), затем в venv:
.\.venv\Scripts\python.exe -m pip install uhd==4.10.0.0

# CUDA (необязательно): cupy-cuda12x<14 для CUDA 12.x, cupy-cuda11x для 11.x.
# Пакеты nvidia-*-cu12 дают cudart/NVRTC без установки всего CUDA Toolkit.
.\.venv\Scripts\python.exe -m pip install "cupy-cuda12x<14" nvidia-cuda-runtime-cu12 nvidia-cuda-nvrtc-cu12 nvidia-nvjitlink-cu12
```

### Linux / macOS

```bash
cd /path/to/GNSS_Sim
./scripts/setup_linux.sh
```

Скрипт создаёт `.venv`, ставит `requirements.txt`; если в системе есть пакет
UHD, ставит `libuhd-dev uhd-host python3-uhd` (apt), пересоздаёт venv с
`--system-site-packages` (чтобы был виден системный `uhd`) и запускает
`uhd_images_downloader`.

Вручную:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt

# UHD (Debian/Ubuntu): пакеты + образы FPGA
sudo apt install libuhd-dev uhd-host python3-uhd
sudo uhd_images_downloader
# системный uhd виден только в venv с --system-site-packages:
python3 -m venv --system-site-packages .venv

# CUDA (необязательно); без системного CUDA Toolkit добавьте runtime-пакеты:
# nvidia-cuda-runtime-cu12 nvidia-cuda-nvrtc-cu12 nvidia-nvjitlink-cu12
.venv/bin/python -m pip install "cupy-cuda12x<14"
```

Если пакетов UHD нет, соберите UHD из исходников с
`-DENABLE_PYTHON_API=ON`, затем `.venv/bin/python -m pip install uhd==4.10.0.0`.
Без UHD всё работает — генерируется IQ-файл (передача на B210 недоступна).

## Запуск GUI

```powershell
cd E:\MySoftware\GNSS_Sim
python run.py
```

`run.py` сам перезапускается проектным интерпретатором
`.venv\Scripts\python.exe` (Linux/macOS — `.venv/bin/python`), поэтому
системный `python` тоже подходит: достаточно, чтобы он был на `PATH`.
Защита от зацикливания — переменная `GNSS_SIM_VENV_REEXEC`. Прямой запуск
`.\.venv\Scripts\python.exe run.py` тоже работает. CLI
(`python -m gnss_sim …`) перезапускается так же. Если нужно только узнать
итоговый интерпретатор (например, в headless-проверке):

```powershell
python run.py --print-interpreter
```

Три вкладки:

* **Генерация** — группа **«Управление воспроизведением»** (кнопки
  «Сгенерировать IQ»/«Старт»/«Пауза»/«Стоп»/«Воспроизвести», галочка
  **«Зациклить сегмент (RAM)»** и выбор **готового IQ-файла** в одном месте),
  прогресс, список видимых спутников и группа **«Приёмник u-blox (COM)»**.
* **Базовые** — эфемериды (или автоскачивание, в т.ч. с CDDIS), координаты
  либо файл движения, время старта (календарь + «Сейчас (UTC)»), длительность,
  набор сигналов, выходной IQ-файл, группа **«Передача на B210 (авто)»** со
  **статусом B210** и **ползунком «Мощность TX»** (строка
  **подпись | ползунок | значение** в дБ, 0..89.75 дБ, по умолчанию +18 дБ).
  Мощность применяется к живому B210 **на лету во время передачи**.
* **Дополнительные** — параметры B210 (канал, антенна, полоса, опорная
  частота), BeiDou/объединение полос, CDDIS и мониторинг RX.

По умолчанию передача **автоматическая**: если B210 обнаружен, «Старт» и
«Воспроизвести» сразу передают в эфир; если нет — только файл, а индикатор на
вкладке «Базовые» объясняет причину. Отдельной
галочки «Передавать на B210» больше нет; кнопка **«Проверить B210»**
перепроверяет наличие устройства.
  У каждой группы настроек есть кнопка **«по умолчанию»**, сбрасывающая только
  её (логин/пароль/токен CDDIS не затрагиваются). Колесо мыши над списками
  (частота дискретизации, центр, формат, источник…) не меняет значение — оно
  работает только при открытом выпадающем списке. Числовые поля
  (**«Маска элевации»**, **«Запас уровня»**, **«Амплитуда»**,
  **«Длительность»**, RX gain и т. п.) тоже игнорируют колесо, пока в них нет
  курсора (фокуса), — прокрутка страницы не меняет настройки случайно.

  Область прогресса показывает **одну** полосу за раз, но сама полоса
  **подменяется** по фазам. Сначала идёт полоса **подготовки/генерации**,
  которая заполняется 0→100 % целиком; когда подготовка завершена (или прямо
  перед первой отправкой сэмплов) её виджет **заменяется** полосой
  **«Передача»**, сброшенной в 0, которая затем заполняется по мере отправки.
  Генерация IQ-файла (без радио) так и остаётся на полосе генерации и
  доводится до 100 %. При **циклической передаче** полоса «передача»
  прокручивается каждый цикл (0→100 % за сегмент), а подпись —
  «циклическая передача» с временем и **номером прохода**, поэтому она не
  «залипает» на 100 %. Журнал больше **не засоряется**: строки
  `Идёт генерация/предгенерация: X% (Y из Z с)` пишутся только на отметках
  25/50/75/100 % или раз в ~30 с. «Стоп» срабатывает не позже одного блока
  генерации. Под прогрессом — компактный индикатор уровня TX/RX
  (`пик/RMS dBFS`, `КЛИП`/`underflow`), обновляется ~2 раза/с.

  Выбранный RINEX связывается с полем времени старта: окно покрытия берётся
  **из фактических эпох RINEX** — нижняя граница = самая ранняя эпоха файла,
  верхняя = самая поздняя (никакого `toe ±6 ч`). При этом **дата старта
  берётся из номера RINEX-файла** (его DOY), а не из самой ранней эпохи: файл
  `BRDC00IGS_R_20262670000_01D_MN.rnx` (DOY 267) показывает **2026/09/24**,
  хотя его ранний `toc` — 23.09 23:30. Дата **заблокирована** (редактируется
  только время HH:MM:SS); окно покрытия показано в той же (UTC) шкале, поэтому
  время можно вводить/крутить в пределах `[начало RINEX, конец RINEX]`, и
  старт с датой из имени файла всегда попадает в валидное окно (важно для
  декодирования эфемерид приёмником ZED-F9P). Если файл **не покрывает
  «Сейчас (UTC)»** (например, старый эфемерид), галочка «Сейчас (UTC)»
  снимается и блокируется, а старт переводится на день файла. Поддерживаются
  merged (`BRDC00IGS_R_{YYYY}{DOY}0000_01D_MN.rnx[.gz]`) и посистемные
  (`brdc{DOY}0.{yy}{n,g,l,c,j}[.gz]`) имена; окно и дата обновляются **сразу**
  при смене пути к файлу — выбор кнопкой «…», ручной ввод, скачивание CDDIS
  или автоскачивание. BeiDou `toe` (BDT) при этом нормализуется в GPS-время.

  Вкладки **«Базовые»** и **«Дополнительные»** синхронизированы по B1I:
  галочка **BeiDou B1I** в «Базовых» — единственный источник истины и
  **по умолчанию снята** (узкая сессия L1, 2.6 Мвыб/с); управляющие B1I поля
  в «Дополнительных» (`Данные B1I`, «Авто-подбор…») доступны только при
  выбранном B1I, а включение «Объединять L1+B1I» автоматически отмечает B1I
  (и снимается вместе с ним) — вкладки не могут разойтись. Пояснения к
  «Сигналам» убраны из формы и перенесены в «Справку»/подсказки.
* **Карта и трек** — карта OpenStreetMap: кликами строится маршрут, задаются
  параметры карьерного самосвала (скорости с грузом/порожняком, ускорения,
  время погрузки/разгрузки, число циклов, уклон). Кнопка **«Рассчитать трек»**
  строит motion-файл (`truck_track.csv`) и подставляет его в сценарий;
  **«Проиграть»** показывает движение машины по карте.
* **Спектр** — график PSD (pyqtgraph): спектр генерируемого TX-сигнала, а при
  включённом мониторинге RX — ещё и спектр принятого сигнала.

## Запуск CLI

```powershell
# Автоскачивание RINEX за нужную дату и IQ в файл (все сигналы, 60 с)
.venv\Scripts\python.exe -m gnss_sim ^
    -t "2022/01/01,00:00:00" -d 60 -o out.cs16 --format cs16

# Свой RINEX-файл и статичная точка
... -m gnss_sim -e gps-sdr-sim\brdc0010.22n -l 35.681298,139.766247,10 -d 60 -o out.cs16

# Движение по треку самосвала
... -m gnss_sim -x truck_track.csv -d 600 -o truck.cs16

# Отключить отдельные системы
... -m gnss_sim --no-galileo --no-sbas --no-qzss -o gps_only.cs16

# Отдельная узкополосная сессия только BeiDou B1I (NH20 + D1, нужен --beidou)
... -m gnss_sim --beidou --band b1i --b1i-data d1 ^
    -e rinex_cache\BRDC00IGS_R_20262660000_01D_MN.rnx ^
    -t "2026/09/23,12:00:00" -d 60 -o b1i.cs16

# Единый поток всех систем одновременно (нужен --beidou; центр/fs вычисляются: ~1571.328 МГц / 25 Мвыб/с)
... -m gnss_sim --beidou --band all -e rinex_cache\BRDC00IGS_R_20262660000_01D_MN.rnx ^
    -t "2026/09/23,12:00:00" -d 10 -o all.cs16

# Передача объединённого потока на B210 (общий TX LO; аттенюатор + DC block!)
... -m gnss_sim --beidou --band all -e rinex_cache\BRDC00IGS_R_20262660000_01D_MN.rnx ^
    -t "2026/09/23,12:00:00" --tx --no-loop -d 10

# B1I без реальных эфемерид (постоянный +1, но со структурой NH20)
... -m gnss_sim --beidou --band b1i --b1i-data placeholder -o b1i_ph.cs16

# Передача на B210 (ОБЯЗАТЕЛЬНО через аттенюатор + DC block!)
# У B210 усиление TX 0..89.75 дБ; отрицательное недопустимо (зажмётся в 0).
# Вниз мощность — только внешним аттенюатором. По умолчанию +18 дБ.
... -m gnss_sim -e rinex_cache\BRDC00IGS_R_20262670000_01D_MN.rnx ^
    -t "2026/09/24,12:00:00" --tx --uhd-args type=b200

# Передать уже готовый IQ-файл: прикрепляется ключом --iq-input (из RAM, зацикливается)
... -m gnss_sim --iq-input out.cs16 --tx --uhd-args type=b200

# Список устройств
... -m gnss_sim --list-devices
```

Амплитуда по умолчанию **автоматическая** (по числу каналов); anti-clip
**по умолчанию выключен** (исторический уровень 0.15 проверен на ZED-F9P).
Явный единый множитель и управление запасом:

```powershell
# Явный общий масштаб (как раньше) — отключает автомасштаб
... -m gnss_sim --amp 0.1 -o out.cs16
# Включить anti-clip (цель пика 0.7) / сменить цель / выключить
... -m gnss_sim --headroom -o out.cs16
... -m gnss_sim --headroom 0.9 -o out.cs16
... -m gnss_sim --no-headroom -o out.cs16
```

Полный список опций: `python -m gnss_sim --help`.

## Повторное использование готового IQ-файла

Вместо генерации можно взять уже готовый IQ-файл (полезно для повторной
передачи записанного сигнала):

```powershell
# CLI: генерация пропускается, файл читается и (при --tx) идёт в эфир
... -m gnss_sim --iq-input out.cs16 --tx --tx-gain 18
# Без --tx файл только проверяется и описывается в журнале
... -m gnss_sim --iq-input out.cs16
```

`gnss_sim/iqfile.py::IqFileSource` читает `cf32`/`cs16`/`cs8`/`cs4`, при этом
формат, `sample_rate`, `center_freq` и `output_scale` берутся из side-car
`<файл>.json` (если он есть); иначе используются значения из настроек и
пишется предупреждение. Готовый IQ-файл **всегда загружается в RAM** и
зацикливается из памяти (при передаче — до «Стоп», длительность/`--no-loop`
учитываются). Буфер хранится в **нативном формате** файла (`cs16` = 4 Б/отсчёт,
`cs8` = 2 Б/отсчёт), поэтому ему нужно ≈ размер файла, а не вчетверо больше;
на каждый блок выделяется лишь небольшой `complex64`-массив. Доступная RAM
проверяется через `sysinfo`, и при нехватке выводится понятная ошибка. Флаг
`--iq-ram` оставлен только для совместимости: воспроизведение теперь всегда
идёт из RAM. RINEX/`SignalEngine` при этом не используются.

> **Готовый IQ-файл нельзя сдвинуть по времени.** В записанном сигнале
> «зашиты» GPS/Galileo TOW/HOW, номера недели и эфемериды того момента, когда
> файл был сгенерирован; при воспроизведении они передаются **как есть**, и
> поле «Время старта» (в CLI `-t`) на них **не влияет**. Поэтому при повторной
> передаче приёмник получит именно записанное время: если эфемериды/время в
> приёмнике не соответствуют ему (или запись старше ~2 ч), фикс не появится.
> Раннер при `--iq-input`/галочке «готовый IQ-файл» пишет об этом в журнал
> (`ВНИМАНИЕ: готовый IQ-файл воспроизводится как записан … не сдвигается`).
> Сдвиг возможен только генерацией новой сессии (`-t` + эфемериды), а не
> смещением уже записанного файла.


## RINEX-эфемериды

Если файл не задан (или включено автоскачивание), имитатор сам загружает
дневной мульти-GNSS broadcast-файл `BRDC00IGS_R_YYYYDOY0000_01D_MN.rnx.gz`
с BKG (основной) или CDDIS (резерв), распаковывает и кэширует в
`rinex_cache/`. Файлы появляются с задержкой ~1 сутки, поэтому пробуются и
предыдущие дни. Поддерживаются системы G (GPS), E (Galileo), J (QZSS),
S (SBAS); RINEX 2 и 3.

**Тип файла важен:** `brdc{doy}0.{yy}n` (`.26n`) — **только GPS**;
`brdc{doy}0.{yy}g` (`.26g`) — **только GLONASS**; merged
`BRDC00IGS_R_…_MN.rnx` — мульти-GNSS (G/E/J/C, предпочтительный). Для
Galileo/BeiDou нужен merged-файл (или посистемный набор `l`/`c`/`j` — см.
ниже); при выборе per-system файла в журнал
пишется «только GPS …». Архивы `.gz` распаковываются прозрачно (детект по
магии `1f 8b` и по расширению), распакованная копия кладётся рядом
(`foo.26n.gz` → `foo.26n`); выбранный файл всегда сопровождается в журнале
списком систем (счёт G/E/J/C).

### Скачивание с CDDIS (логин/пароль, выбор даты)

CDDIS (Earthdata) требует авторизации. Дневные файлы лежат по адресу
`https://cddis.nasa.gov/archive/gnss/data/daily/{yyyy}/brdc/` (без папки DOY):

* `BRDC00IGS_R_{yyyy}{doy:03d}0000_01D_MN.rnx.gz` — мульти-GNSS;
* `brdc{doy:03d}0.{yy:02d}n.gz` — GPS RINEX 2;
* `brdc{doy:03d}0.{yy:02d}g.gz` — ГЛОНАСС RINEX 2;
* `brdc{doy:03d}0.{yy:02d}l.gz` / `.c.gz` / `.j.gz` — Galileo / BeiDou / QZSS.

**Мультисистемный `BRDC00IGS_R_…_MN.rnx` публикуется только за прошедшие
сутки.** Поэтому для текущей даты (UTC) merged обычно отдаёт 404, и программа
берёт посистемный набор `brdc{DOY}0.{yy}{n,g,l,c,j}`: скачивает все уже
выложенные файлы, распаковывает их в `rinex_cache/` и парсит вместе
(`parse_nav_file` принимает список путей и объединяет эфемериды). 404-ответы
считаются и логируются один раз, а не по каждому URL. В GUI над кнопкой
«Скачать за дату» есть заметка об этом; в журнал пишется понятное сообщение,
например `CDDIS: мультисистемный BRDC00IGS доступен только за прошедшие
сутки; для текущей даты берём посистемные brdc{DOY}0.{yy}{n,g,l,c,j}`.
Например, для 2026-09-21 (DOY 264): `brdc2640.26n.gz`, `brdc2640.26g.gz`.

Скачивание идёт через `urllib` с cookie-jar и HTTP Basic (редирект на
`urs.earthdata.nasa.gov` и обратно); можно вместо логина/пароля указать
bearer-токен. `.gz` распаковывается в `rinex_cache/`.

CLI:

```powershell
# Скачать за конкретную дату (source=cddis) с логином/паролем Earthdata
... -m gnss_sim --source cddis --cddis-user МОЙ_ЛОГИН ^
    --cddis-password ПАРОЛЬ -t "2026/09/21,00:00:00" -d 60 -o out.cs16

# Или по bearer-токену
... -m gnss_sim --source cddis --cddis-token ТОКЕН ...

# Источник: auto (по умолчанию, BKG + CDDIS при наличии данных входа),
# bkg — только BKG, cddis — только CDDIS
... -m gnss_sim --source bkg -t "2026/09/21,00:00:00" -d 60
```

GUI (группа **«Эфемериды и позиция»**): список «Источник эфемерид»
(`auto`/`bkg`/`cddis`), поля **CDDIS логин**, **CDDIS пароль** (скрытый), **CDDIS
токен** (необязательно), поле **Дата CDDIS** (`YYYY/MM/DD`, подставляется из
времени старта) и кнопка **«Скачать за дату»**: дата превращается в DOY,
загрузка идёт в фоновом потоке, а готовый файл подставляется в «RINEX
navigation».

### Спектр (PSD)

Вкладка **«Спектр»** показывает спектральную плотность мощности (метод Уэлча,
окно Ханна, 50 % перекрытия — `gnss_sim.power.welch_psd`, чистый NumPy без
SciPy) на осях «частота, МГц» / «PSD, dBFS». Во время генерации обновляется
кривая **TX** (блок ≤65536 отсчётов примерно раз в 0.5 с); при включённой
галочке «Слушать RX» добавляется кривая **RX**. График строится на
`pyqtgraph` (`gnss_sim/spectrum.py`) и работает в offscreen-режиме (тесты без
дисплея).

### Приёмник u-blox ZED-F9P (COM)

Группа **«Приёмник u-blox (COM)»** на вкладке «Генерация» читает NMEA с
ZED-F9P по COM-порту (`gnss_sim/ublox.py`, pyserial). Выберите порт (список
из `list_ports`, по умолчанию `COM3`) и скорость (9600/38400/115200/460800,
по умолчанию 38400), нажмите **«Подключить»**. Раз в 0.5 с обновляются строка
состояния (lat/lon/высота, UTC, fix, число спутников, HDOP) и таблица видимых
спутников (система, PRN, элевация, азимут, SNR). Каждые ~2 с в журнал
дополнительно пишется **сравнение передаваемого списка с GSV приёмника**
(`ublox.compare_visible`): `Видимые (симулятор vs GSV): N передано,
M в GSV, совпало K; нет в GSV: …; нет в симуляторе: …`. Сравнение идёт
именно с **GSV** (спутники «в поле зрения»), а **не с GSA** (там только
используемые в решении — иначе отслеживаемые, но не задействованные спутники
были бы не видны). «Нет в GSV» — диагностический признак: имитатор передаёт,
а приёмник не видит/не следит. Кнопки **«Взять позицию из
приёмника»** и **«Взять время из приёмника»** подставляют координаты в
`Широта/Долгота/Высота`, а время — в «Время старта». Если COM-порта нет,
приложение выводит сообщение и продолжает работать.

**Если ZED-F9P даёт только 2D-fix.** Проверьте, что дата старта совпадает с
днём RINEX-файла (см. выше: она берётся из номера файла, а не из раннего `toc`)
и что старт лежит внутри окна покрытия — иначе приёмник не примет эфемериды,
получит лишь часть спутников и уйдёт в 2D. Недельный номер подкадров 1 и TOW
формируются из времени старта (`generate_nav_msg(transmit_week=start.week)`),
для старта 2026-09-24 это GPS-неделя 2437 (`%1024 = 389`); это проверяется
headless-тестом. Более «частая» причина 2D — старый RINEX: при RTC приёмника,
близких к реальному времени, эфемериды суточной давности он считает
устаревшими. Короткая диагностика (не запускать долго): передайте ~20–30 с,
затем в u-center посмотрите `UBX-NAV-SAT`/`UBX-NAV-PVT` — если валидных
эфемерид (`eph` = yes) меньше 4, а `toc` сильно в прошлом, используйте
свежий файл (для текущих суток — посистемные `brdc{DOY}0.{yy}*`).

## Амплитуда и защита от клиппинга (headroom)

Композитный baseband суммируется по всем каналам, поэтому одна и та же
`--amp 0.15` на многосистемной сцене давала пик ≈1.86 (клиппинг ЦАП B210), а на
GPS-only L1 C/A — ≈0.82. Теперь работают два независимых механизма:

* **Автомасштаб амплитуды** (`--amp` не задан; в GUI — галочка **«Авто»**).
  Из аллоцированных каналов берётся сумма их весов (дальность × диаграмма
  направленности) и выбирается **один** множитель так, чтобы оценённый пик не
  превышал полную шкалу: многосистемная сцена получает ≈0.03–0.06, GPS-only
  L1 C/A — ≈0.08–0.13. Явный `--amp 0.1` (или снятая галочка «Авто» и значение
  в поле «Амплитуда») по-прежнему задаёт ровно один общий множитель для всех
  каналов. Без автомасштаба многосистемная сцена уже не клиппует.
* **Автоматический запас по уровню (anti-clip, `--headroom`, по умолчанию
  выключен; при включении цель пика `0.7`).** Если сегмент предгенерён в RAM (циклическая
  передача на B210 и `--no-loop` TX), измеряется **точный глобальный пик
  сегмента** и на весь сегмент накладывается **один** масштаб — на эфире нет
  скачков уровня. Без предгенерации (потоковая передача) масштаб выводится из
  первых блоков и только уменьшается, если очередной блок грозил бы
  клиппингом. Запас применяется и к IQ-файлу, поэтому итоговый файл также не
  содержит клиппинг.

В журнал пишется применённый масштаб и peak/RMS (dBFS) до/после вместе со
счётчиком клиппованных отсчётов (`|x| > 1`), например:
`TX headroom (сегмент): масштаб 0.7591 (цель пика 0.700); до: пик 0.922
(пик -0.7 dBFS), RMS 0.252 (-12.0 dBFS), клип 0; после: пик 0.700
(пик -3.1 dBFS), RMS 0.191 (-14.4 dBFS), клип 0`.
Включить: `--headroom` (цель `0.7`); сменить цель или выключить:
`--headroom 0.9`, `--no-headroom`.
Передача на B210 идёт блоками не более **100 мс** (запись файла — 500 мс,
`--block-ms`), что уменьшает underflow на USB3.

GUI: группа «Сигналы» — галочка **«Авто»** рядом с полем «Амплитуда» и блок
**«Запас уровня (anti-clip)»** с целевым пиком. На вкладке «Генерация» под
прогрессом есть компактный индикатор уровня
`TX: пик -3.1 dBFS, RMS -14.4 dBFS` (обновляется ~2 раза/с, не по отсчёту);
при клиппинге добавляется `КЛИП N`, при передаче на B210 — `underflow N`.
Шкала dBFS та же (комплексный тон амплитуды 1.0 = 0 dBFS).

## Модель самосвала

Рейс по замкнутому маршруту (haul cycle): гружёный ход со скоростью
`v_laden`, разгрузка, порожний возврат со скоростью `v_empty`, погрузка; далее
повтор `cycles` раз. Скорость на поворотах ограничивается из радиуса
кривизны и бокового ускорения, есть ограничение разгона/торможения и тормозной
«просмотр» вперёд до остановки у конца плеча. Высота меняется линейно по
заданному уклону (`grade_pct`). Motion-файл — `lat;lon;h` на 10 Гц, совместим
с `motion.py`.

## Безопасность при передаче

Передача на частоте GPS без экранирования запрещена. Соединяйте TX B210 с
приёмником через **аттенюатор 50–60 дБ и DC block**, либо используйте
кабельное подключение в экранированной лаборатории. Ответственность за
соблюдение местных норм — на операторе.

## Нативная передача TX (25 Мвыб/с без underflow)

Python-петля UHD на ~25 Мвыб/с (объединённый поток L1+B1I) давала underflow
(≈100–200 за 1–2 мин) из-за накладных расходов на блок. Для устойчивой передачи
есть нативный помощник **`native/gnss_sim_tx.exe`**: он играет готовый
`cs16`-файл из плотной C++-петли UHD (без Python/GIL между отправками).

Сборка (MSVC + UHD; UHD `include`/`lib`/`bin` подхватываются из `UHD_PKG_PATH`
или `C:\Program Files\UHD`):

```powershell
native\build.bat     # -> native\gnss_sim_tx.exe
```

Подключение из CLI — флаг `--tx-native`; в GUI — галочка «Нативная передача»
(**по умолчанию снята**: это явный opt-in, наличие `gnss_sim_tx.exe` её только
разрешает). По умолчанию передача идёт встроенным Python-путём UHD:

```powershell
.venv\Scripts\python.exe -m gnss_sim --beidou --combine ^
    -e rinex_cache\BRDC00IGS_R_20262670000_01D_MN.rnx ^
    -t "2026/09/24,12:00:00" -d 60 --tx --tx-native --tx-gain 40 ^
    --uhd-args "type=b200,serial=000000372"
```

Раннер сам предгенерирует сегмент во временный `cs16`-файл, запускает помощник
(с `--loop` при включённой галочке «Зациклить»), пишет его stderr в журнал и
показывает счётчик underflow. Если `gnss_sim_tx.exe` не собран — понятный откат
на встроенный Python-путь UHD.

Прямой запуск (например, для уже готового IQ-файла):

```powershell
set PATH=C:\Program Files\UHD\bin;%PATH%
native\gnss_sim_tx.exe --file out.cs16 --rate 25e6 --freq 1571.328e6 ^
    --gain 40 --antenna TX/RX --args "type=b200,serial=000000372" --seconds 60
```

Крупные кадры (`--frame-size 16384`; UHD сам фрагментирует их) + приоритет
процесса снижают underflow до нуля на 25 Мвыб/с. Замечание по сборке: публичные
C++-заголовки UHD требуют Boost, которого нет в Windows-инсталляторе, поэтому
помощник вызывает стабильный C ABI UHD (`uhd_usrp_*`, `uhd_tx_streamer_*`) —
тот же `multi_usrp`/`tx_streamer` внутри.

## Мониторинг RX, регулятор мощности и эхо в камере

При передаче на B210 можно **одновременно принимать** сигнал на другом
канале — контролировать собственный TX, измерять уровень и SNR, автоматически
подбирать усиление и оценивать эхо/многолучёвость (например, в безэховой
камере). Реализация: `power.py` (чистый NumPy: `rms_dbfs`, `PowerRegulator`,
`delay_profile`, `estimate_noise_floor`) и `uhd_duplex.py` (ленивый `import
uhd`).

### Физика B210: порты и гетеродины

B210 = один AD9361 с **раздельными LO приёма и передачи**: RX и TX могут
работать одновременно и на разных частотах (FDD). Важные ограничения:

* у канала 0 порт `TX/RX` один (TDD-переключатель) — **нельзя слушать свой
  TX на том же канале/порту**;
* для контроля передачи: **TX на `tx_channel` (порт `TX/RX`)**, **RX на
  другом канале (порт `RX2`)** через кабель/ответвитель или антенну;
* один RX LO общий для обоих RX-каналов, один TX LO — для обоих TX-каналов;
* одноимённые TX и RX каналы запрещены (программа выдаст понятную ошибку).

### Замкнутый контур мощности

Регулятор (`PowerRegulator`) измеряет уровень RX и подстраивает `tx_gain`
ограниченным пропорциональным шагом с EMA-сглаживанием и мёртвой зоной, чтобы
не раскачиваться. Шумовой пол измеряется один раз перед стартом передачи (TX
ещё выключен); SNR = уровень RX − шумовой пол. Шкала dBFS: комплексный тон
амплитуды 1.0 = 0 dBFS.

### Запуск (CLI)

```powershell
# TX на канале 0 (TX/RX), RX на канале 1 (RX2), авторегулятор до -30 dBFS,
# профиль задержек (топ-3 эхо) — ОБЯЗАТЕЛЬНО аттенюатор 50-60 дБ + DC block!
.venv\Scripts\python.exe -m gnss_sim ^
    --tx --monitor --tx-channel 0 --tx-gain 18 ^
    --rx-channel 1 --rx-ant RX2 --rx-gain 30 ^
    --tx-power-target -30 --echo ^
    -t "2022/01/01,00:00:00" -d 600

# Только измерение, без автоподстройки; RX в стороне от TX (шумовой пол)
... -m gnss_sim --tx --monitor --no-tx-power-auto --rx-freq 1570e6

# Обычная передача без мониторинга (поведение не изменилось)
... -m gnss_sim --tx --tx-gain 18
```

В журнал раз в ~0.5 с пишется строка вида
`RX: -29.7 dBFS, шум -105.2 dBFS, SNR 75.5 дБ`. При включённом эхо-анализе:
`Эхо, топ-3: 0 нс / 0.0 дБ, 348 нс / -6.1 дБ, 1210 нс / -12.4 дБ`.

### GUI

Группа **«Мониторинг RX / мощность»**: галочка `cb_monitor` (слушать RX на
другом канале), цель `sp_target` (dBFS), `cb_auto` (авторегулятор TX gain),
`sp_rx_ch` (0…1), `ed_rx_ant` (порт, по умолчанию `RX2`), `sp_rx_gain`,
`sp_rx_freq` (0 = как TX) и `cb_echo` (профиль задержек).

### Безопасность

Контрольный RX-вход подключайте **только через аттенюатор 50–60 дБ** (и DC
block): без него мощность TX перегрузит вход приёмника. При работе «в
камеру» используйте экранированный объём и минимально возможное усиление.

## Производительность и CUDA

Синтез отсчётов можно выполнять на CPU (NumPy) или на GPU (CUDA через CuPy).
Бэкенд выбирается автоматически: если найден GPU NVIDIA и установлен
`cupy-cuda12x`, используется CUDA, иначе CPU. Явный выбор — `--backend
auto|cpu|cuda` в CLI или список «Бэкенд синтеза» в GUI.

Замеры при `fs = 2.6 МГц`, 27 каналов (GPS + Galileo + QZSS + SBAS),
старт Tokyo 2022/01/01:

| Бэкенд | Скорость | 6000 с файла | Размер (`cs16`) |
|---|---|---|---|
| CPU (NumPy, `complex128`) | ≈0.13× реального времени | ≈13 ч | 62.4 ГБ |
| CUDA (RTX 4080, блок 500 мс, `complex64`) | ≈9–17× реального времени | ≈10–15 мин | 62.4 ГБ |

CUDA использует `complex64`/`float32`; отличие от CPU-тракта `complex128`
по нормированной корреляции ≈0.999, что для имитации сигнала несущественно.
Для длинных файлов всё упирается в диск: при 2.6 Мвыб/с `cs16` = 10.4 МБ/с
(6000 с ≈ 62 ГБ), `cs8` = 5.2 МБ/с. Рекомендуемый размер блока генерации —
500 мс; ожидаемый размер файла печатается в журнал перед записью.

## RAM, длительность и зацикливание

**Длительность по умолчанию — 120 с** (в GUI, CLI `-d`/`--duration` и
`SimConfig.duration`).

Длинная запись (до 6000 с) упирается и в объём, и в пропускную способность
диска, поэтому есть режим **зацикливания (включён по умолчанию)**:

- приложение анализирует RAM (всего/доступно) и задаёт бюджет — 60 % доступной
  памяти (в CLI можно задать `--memory-budget`, ГБ; в GUI отдельного поля нет);
- считается, сколько секунд сигнала в этот бюджет влезает (для `cs16` при
  `fs = 2.6 МГц` это ≈10.4 МБ/с);
- автоматическая длина сегмента = `min(длительность, что влезает в RAM)`.
  Если заданная длительность **помещается** — генерируется ровно она (один
  сегмент), даже при включённом зацикливании; урезание (с предупреждением)
  происходит только при нехватке RAM, и тогда длина округляется вниз до
  кратного 30/18 с (90 с), как раньше;
- в файл пишется только сегмент; при передаче на B210 сегмент проигрывается
  из RAM по кругу (диск не нужен); готовый IQ-файл всегда загружается в RAM и
  зацикливается из памяти (буфер — в нативном формате, ≈ размер файла). В
  журнал пишется, откуда идёт воспроизведение;
- проверка «Стоп» выполняется не реже, чем раз в блок генерации
  (`--block-ms`), поэтому остановка срабатывает быстро — в том числе из паузы;
- прогресс-бар заполняется на каждом сгенерированном блоке (в т.ч. при записи
  длинного зацикленного сегмента в файл), а строка
  `Идёт генерация: X% (Y из Z с)` — только на отметках 25/50/75/100 % или раз
  в ~30 с, чтобы не засорять журнал;
- перед записью в журнал выводятся: доступная RAM, бюджет, максимум секунд,
  свободное место на диске и ожидаемый размер.

Параметры: `--loop-seconds` (0 = авто), `--memory-budget` (ГБ, 0 = 60 % RAM),
`--no-loop` (полная запись без зацикливания). В GUI поле «Длина сегмента»,
«Бюджет RAM» и отдельная галочка «Загрузить IQ в RAM» убраны (бюджет
вычисляется автоматически, готовый IQ всегда идёт из RAM); на вкладке
**«Генерация»** в одной группе **«Управление воспроизведением»** находятся
кнопки, галочка **«Зациклить сегмент (RAM)»** и выбор готового IQ-файла, а
строка состояния RAM — в группе «Выход IQ».
Для длинной записи предпочтителен **RAM-диск** (например, ImDisk/OSFMount на
Windows или `/dev/shm` на Linux): путь к нему просто указывается в поле файла,
а приложение проверяет его свободное место.

При стыке сегментов возможен скачок фазы несущей (разные доплеры у разных
спутников не дают строго периодического сигнала) — приёмник обычно
удерживает захват; при необходимости уменьшайте `--loop-seconds`.

## Диапазоны/сессии

BeiDou B1I (1561.098 МГц) отстоит от центра L1 (1575.42 МГц) на 14.322 МГц,
поэтому в узкой полосе L1 он не помещается. Совмещение всех сигналов требует
широкой полосы, а у B210 **один общий TX LO** — все диапазоны должны идти
одним потоком. Поэтому сессия выводится из выбранных систем:

| Сессия | Центр | fs | Системы |
|---|---|---|---|
| `l1` | 1575.42 МГц | 2.6 Мвыб/с (не расширяется под L1C/CBOC) | GPS/Galileo/QZSS/SBAS |
| `b1i` | 1561.098 МГц | 4.092 Мвыб/с | только BeiDou B1I |
| `all` | ≈1571.33 МГц | ≈25 Мвыб/с | все включённые (opt-in: CLI `--beidou --band all`) |
| `wide` | = `all` | = `all` | устаревший синоним `all` |

**В GUI отдельного выбора «Диапазон/сессия» и «Режим эфемерид» больше нет.**
Галочки «Сигналы» — единственный источник истины: из них выводятся сессия,
центр/`fs` (поля только для чтения) и режим RINEX (мультисистемный merged,
если отмечены Galileo/QZSS/BeiDou, иначе GPS-only). Ручная пересборка полосы
осталась только в CLI.

### Объединённый поток `all` (opt-in)

Полоса L1 по умолчанию **не** расширяется под боковые лепестки BOC(6,1):
L1C TMBOC(6,1) и Galileo E1 CBOC(6,1) считаются как ±1.023 МГц вокруг
1575.42 МГц, поэтому L1-группа (GPS L1 C/A + L1C + Galileo E1 + QZSS + SBAS)
остаётся на **2.6 Мвыб/с / 1575.42 МГц** — как и раньше.

Только при явном включении объединённого потока (галочка «Объединять L1+B1I»;
CLI — `--combine`, или `--band all`/`wide`, обязательно вместе с `--beidou`)
полуширины берутся полными:

* GPS/QZSS L1 C/A и SBAS — ±1.023 МГц вокруг 1575.42 МГц;
* GPS/QZSS L1C TMBOC(6,1) и Galileo E1 CBOC(6,1) — ±8.184 МГц (лепестки
  BOC(6,1));
* BeiDou B1I — ±2.046 МГц вокруг 1561.098 МГц.

`центр = (min+max)/2`, `fs = round_up(max−min)·1.05`, затем `fs`
округляется к удобному для B210 значению и ограничивается диапазоном
2.6…56 Мвыб/с. Для всех пяти систем: min = 1559.052 МГц,
max = 1583.604 МГц, размах 24.552 МГц → **центр 1571.328 МГц, fs 25 Мвыб/с**
(лог печатает расчёт и предупреждение о длительной предгенерации в RAM).
GUI показывает вычисленные значения в read-only полях «Радиотракт
(вычисляется)» и в блоке «Сигналы».

Выбор сессии (CLI `--band l1|b1i|all|wide`) задаёт рекомендованные центр и
`fs`; явные `-s/--sample-rate` и `-f/--center-freq` переопределяют значения из
`--band` (в сессии `all` ручные значения не заменяются авто-подбором).

* В сессии **`l1`** включённый BeiDou **отключается** с понятным сообщением и
  **не** переключает `fs` на широкую полосу.
* Сессия **`b1i`** включает только BeiDou и генерирует реальный D1
  (по умолчанию `--b1i-data d1`; `placeholder` — постоянный +1 со структурой
  NH20).

Старые флаги `--auto-b1i` / `--no-auto-b1i` и галочка «Авто-подбор fs/центра
под B1I» сохранены для совместимости (действуют только при ручных `-s`/`-f`),
но в сессии `l1` больше не расширяют полосу.

### Консоль, UHD и маркеры `U`/`O`

UHD пишет `[INFO]`/`[WARNING]` в **stderr**; в PowerShell это выглядит как
оранжевый `NativeCommandError` даже при коде выхода 0. При старте программа
перехватывает нативный stderr. Важно: раньше при этом ставился
`UHD_LOG_LEVEL=fatal` (самый тихий уровень) — и UHD вообще ничего не писал, так
что в журнале GUI не было ни одной строки UHD, хотя offscreen-тесты (они пишут
в fd 2 напрямую) проходили. Теперь и **GUI, и CLI по умолчанию запрашивают
`UHD_LOG_LEVEL=info`** (`nativelog.DEFAULT_UHD_LOG_LEVEL` /
`GUI_UHD_LOG_LEVEL`), поэтому `[INFO]`-строки UHD **видны**: в GUI — в
журнале, в CLI — на **stdout** (перехватчик перенаправляет весь нативный stderr
в stdout, а не в реальный терминал). Уровень переопределяется флагом
`--uhd-log-level` (`fatal`/`error`/`warning`/`info`/`debug`). Отдельно:
async-обработчик B200 (`standard_async_msg_prints`) пишет одиночные символы
**`U`/`O`/`L`** (underflow/overflow/late) напрямую в `std::cerr` в обход уровня
логов — их фильтрует перехватчик, а настоящие нативные сообщения попадают в
журнал GUI/на stdout. Перехваченный поток
**направляется прямо в журнал GUI** (в GUI-режиме) и обрабатывается построчно:
строки без тега `[WARNING]`/`[ERROR]` выводятся обычным (неоранжевым) цветом —
даже если в них случайно есть слово `error`/`ошибка`; оранжевым/красным
подсвечиваются только настоящие предупреждения/ошибки. Многострочные куски
разбиваются по строкам, и цвет не «протекает» дальше. Python-биндинги UHD 4.10 не
предоставляют API логирования, поэтому используется переменная окружения
(`--uhd-log-level` переопределяет). На Windows `STD_ERROR_HANDLE`
перенаправляется на **валидный** дескриптор канала уже после `dup2`, а не на
закрываемый `write`-конец (иначе `std::cerr` самой UHD писал в мёртвый handle
и нативные строки не доходили до журнала); если у GUI нет fd 2 (`pythonw`),
fd 2 предварительно открывается на `NUL`, чтобы перехват всё равно встал.
Сквозной offscreen-тест поднимает реальный `MainWindow`, пишет строку через
fd&nbsp;2 и через `GetStdHandle(-12)` и проверяет, что **обе** попали именно в
журнал GUI (обычная — без цвета, `[WARNING]` — оранжевым). Диагностика
симулятора идёт только в stdout/GUI-журнал, в stderr — ничего (кроме сторонних
процессов).

### Передача объединённого потока на B210

TX предгенеряет сегмент в RAM (complex64, 8 Б/отсчёт), затем отдельный
поток-передатчик отдаёт его в UHD без синтеза между блоками; размер сегмента
и оценка времени предгенерации пишутся в лог. На Windows предгенерация 10 с
при 25 Мвыб/с занимает ≈9 с (RTX 4080), передача идёт в реальном времени.
Если синтез медленнее реального времени, печатается предупреждение с
измеренным коэффициентом. Число underflow считается через async-очередь UHD
(в Python-биндингах UHD 4.x у `TXMetadata` нет `error_code`) и всегда
выводится в лог («TX underflow за сеанс: N»); при `N>0` добавляется
предупреждение, данные сегмента при этом не прерываются
(`LIBUSB_TRANSFER_NO_DEVICE` не возникает).

**Путь передачи `--tx-pregen` (один предгенерённый сегмент).** Для короткого
комбинированного прогона (когда вся длительность помещается в бюджет RAM)
runner автоматически выбирает путь «сначала синтезировать весь сегмент в RAM,
затем стримить его без синтеза между блоками» и пишет в лог
`TX: путь — единый предгенерённый RAM-сегмент: предгенерация N с в RAM …`.
Флаг `--tx-pregen` форсирует этот путь: если запрошенная длительность не
влезает в бюджет RAM, она **сокращается** до максимально возможной (вместо
блокировки или перехода на живой синтез) с явным сообщением. Долгие и
циклические прогоны по-прежнему идут «живым» путём (предгенерация первого
сегмента + непрерывный потоковый синтез, лог `TX: путь — живой цикл`).

**Метки времени underflow и журнал здоровья TX.** Каждый зафиксированный
underflow теперь пишется отдельной строкой с **временем симуляции** (с от
начала передачи, `отсчёты/fs`) и **настенным временем**:
`TX underflow #3: sim 272.9 с (от начала TX), wall 12:34:56 — короткий
разрыв потока`; полная история `(sim, wall, счётчик)` доступна как
`UhdTxSink.underflow_events`, а итоговая строка `_report_underflows`
перечисляет sim-времена. Дополнительно во время передачи раз в ~8 с
пишется компактная строка здоровья
`TX health: sim X с | underflow +d (всего N) | выдано B бл., в очереди Q бл. |
синтез Sx, эфир Ax`, а при исчерпании предгенерённого RAM-сегмента —
`TX: предгенерённый RAM-сегмент исчерпан — переход на потоковый синтез`.
Это позволяет отличить настоящий разрыв потока (растут underflow, очередь
пустеет, «эфир» < 1.0x) от пропадания решения на приёмнике (поток идёт
~1.00x, очередь в норме, underflow не растут).

**Разбор трёх «непограничных» пропаданий PVT (760 с).** В прогоне на B210
(Galileo 8 SV, первые 3D через ~50.9 с, чистые 720 с) приёмник терял решение
на 272.9→430.0, 440.5→508.5 и одну секунду около 628.5 с, при этом GSV
показывал C/N0 43–45 дБ-Гц и 9–12 GPS / 3–5 Galileo в поле зрения, а UHD
зарегистрировал лишь 5 underflow (ранее без меток времени). Оффлайн-прогон
800 с той же сцены (RINEX DOY267, старт 2026/09/24 12:00:00, 60/30/100) с
пошаговой проверкой всех систем показал: `engine.g.sec` строго монотонно,
кадровые эпохи 30/18/6 с продвигаются только на номинальный шаг, TOW
подкадра 1 GPS совпадает с эпохой кадра, эфемериды каналов не меняются
(выбор по `toe`/`toc` делается один раз при аллокации, `_roll_frames` их
не перевыбирает), сбросов фазы кода/несущей нет. Ни один roll не привязан
к 272.9/440.5/628.5 с (ближайшие 30-с границы — в 2–10 с от них). Ключевой
факт: 272.9 с лежит **внутри** предгенерённого в RAM 360-с сегмента, где
синтез между блоками вообще не выполняется, — значит поток там
гарантированно непрерывен, и пропадания имеют приёмную/канальную природу
(трекинг, USB3-задержки/повторы, помехи), а не сбой генератора. Регрессия
`tests/test_nav_roll_continuity.py` держит непрерывность 800 с.

**Запас против underflow (приоритет + буфер джиттера).** В циклической
передаче первый сегмент берётся из RAM, а последующие синтезируются
потоком-синтезатором (`_run_tx_segment_loop`), который при этом поднимает
свой OS-приоритет (Windows `SetThreadPriority(THREAD_PRIORITY_HIGHEST)`,
Linux `nice -10`; см. `gnss_sim/rtprio.py`) — тот же приоритет у потока-отправителя
UHD. Между синтезом и UHD стоит ограниченная очередь-«джиттер-буфер»: по
умолчанию **20 с** (было 5 с — пяти секунд не хватало, чтобы пережить редкий
стоп GPU/планировщика, и на границе сегмента возникал underflow), настраивается
`--tx-jitter СЕК` (`runner._tx_jitter_seconds`), автоматически урезается до
~25 % бюджета RAM. Размер буфера пишется в лог. Число underflow после этого
должно оставаться нулевым; при `N>0` проверьте USB3/питание и уменьшите `fs`.

**Циклическая передача непрерывна по времени.** Старый путь «записал сегмент
→ проиграл его по кругу» сбрасывал GPS TOW/HOW на каждой границе (фикс
приёмника терялся примерно на 400-й секунде). Теперь проходы синтезируются
непрерывно из того же движка: TOW/HOW, подкадры NAV 30/18/6 с и фазы
кода/несущей не сбрасываются (проверяется тестом
`tests/test_time_continuous_loop.py`). Ширина окна в 400 с — это длина
сегмента, выбранная `_plan` (`auto_segment_seconds`, кратно 90 с при нехватке
RAM), а не отдельная ошибка.


### BeiDou B1I: NH20 и сообщение D1

* **Вторичный код NH20** (`00000100110101001110`, 1 кбит/с, 20 мс) наложен на
  первичный код; период NH совпадает с длительностью одного бита D1 (50 бит/с).
* **D1**: кадр 1500 бит / 30 с = 5 подкадров по 300 бит / 6 с; слово —
  30 бит. Слова 2…10 — две группы BCH(15,11,1) (`g(X)=X⁴+X+1`) с
  30-битным чередованием; слово 1 — 15 «сырых» бит (преамбула
  `11100010010`) + одна группа BCH. Подкадры 1–3 несут эфемериды и часы
  (`toe/toc/af0..af2`, `WN`, `AODE/AODC`, `URAI`, кеплеровы элементы).
* `self_test` проверяет NH/преамбулу, исправление однократных ошибок BCH,
  обратимость чередования и полный round-trip подкадра (сборка → разбор).
  Позиции/масштабы полей взяты из GNSS-SDRLIB (`sdrnav_bds.c`) и GNSS-SDR
  (`Beidou_DNAV.h`); независимой проверки по «живому» приёмнику нет.
